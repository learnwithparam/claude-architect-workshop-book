      Team enablement

      Enforce in managed settings and hooks, not in CLAUDE.md

      Lumen Supply writes "never push to main" in CLAUDE.md for ten teams, and one team's agent pushes to main anyway. A line in CLAUDE.md is a request, and a team can write a line of its own beside it. This lesson moves the rule to the managed settings and a hook, and writes the baseline that shows whether the rollout helped. This is the Lumen shop repo, with a bare remote to push to. You will watch Claude Code try a push, a change to the secrets file and a normal edit, first under CLAUDE.md alone and then under managed settings.

      I doWatch the failure and its fix.

      Ten teams, one rule, one push

      Claude Code reads CLAUDE.md as context. It does not enforce it. The managed settings are a file the team cannot override, and they hold permission rules and hooks that run at the point of the call.

      Three things go wrong. The rule lives in CLAUDE.md, where any team can add a line that overrides it. Nothing stops the push at the moment it happens. And nobody measured how long a review takes before the rollout, so nobody can say it helped.

      Precedence and the hook, written as code

      Managed settings win over project and user settings, so a team cannot switch the rule off in its own repo. A permission rule matches a command by its prefix. A hook is a script that reads the call and exits with code 2 to block it, and any other code lets it run.

      The starting check raises an error and blocks nothing.

      The fix has three parts. A deny rule refuses the push. A PreToolUse hook exits with 2 on a push to main or a change to .env. A Stop hook refuses to finish with an empty README.

      Managed settings, a hook and a baseline

      The managed settings.json denies git push origin main and any write to .env. A prefix rule is narrow, so it misses a push of HEAD:main or a push with a flag between the words. The hook closes that gap by matching the shape of the command, and the Stop hook gates the finish.

      In the recording the hook's refusal came back, not the deny rule's, because the hook runs first. The two are layers. Cost is small against the failure: the rule is a few lines, and a push to main means a revert, a review and an incident.

      The enablement plan

      A rollout that claims a gain needs something to compare with. The plan records how long a pull request waits for review today, for each team, with a unit. The same measure comes after, so a change can be reported per team.

      Each rollout step names an owner, so a blocked team knows who to ask. The starting plan has no baseline and lets teams start whenever they like.

      The fixed plan ships the review prompt as a shared Skill from the settings repo. Every team loads one copy, and each change is reviewed, since ten hand-edited copies drift. The rollout guide sits beside the settings there, not in a chat a new team never sees.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. The Lumen platform team wants "never push to main" to hold for all 10 teams, and today it is one line in the shared CLAUDE.md. Last week one team's agent pushed to main anyway, so the gap must close before the Friday release freeze, and no team may be asked to change anything. Where should the rule move?

      1. AKeep it in CLAUDE.md and make the wording stronger, so the agent treats it as a hard rule.
      2. BLeave it in CLAUDE.md and add a reviewer who reads each pushed commit after the release.
      3. CAdd a deny rule to the managed settings, so a push to main is refused before it runs.
      4. DAdd the rule to each team's project settings, and ask each team lead to keep it there.
      Show the answer

      Answer: C

      • A Stronger wording is still a request. CLAUDE.md is context the model reads, and a team line beside it can overrule the rule.
      • B A reviewer after the push finds the problem late. The push has already landed, and the freeze deadline is missed.
      • C Correct. A deny rule in the managed settings is enforced at the call, and no team has to change anything.
      • D Project settings sit below the managed ones, and each team lead can edit their own file. That is the override the rule must not allow.

      2. One Lumen team added "Bash(git push:*)" to its project settings so that releases are quick. The platform team has a managed deny rule for "Bash(git push origin main:*)". It must be sure that the team's allow does not weaken it in any of the 10 repos. Which statement describes what happens to a push to main in that repo?

      1. AThe managed deny rule wins, since managed settings outrank project and user settings.
      2. BThe project allow wins, because the setting closest to the repo is the most specific one.
      3. CThe CLAUDE.md in the repo decides, because it is read last and holds the final word.
      4. DThe push runs, because an allow rule always cancels a deny rule in the same session.
      Show the answer

      Answer: A

      • A Correct. Managed settings sit at the top of the precedence order, so a project allow cannot cancel the platform deny.
      • B Closeness to the repo does not rank a setting above the managed one. The managed file has the highest precedence.
      • C CLAUDE.md is context, not a permission source. It never overrides a deny rule.
      • D A deny rule is checked before an allow, and a managed deny cannot be undone by a lower level.

      3. A platform engineer writes a PreToolUse hook that looks for a push to main and prints "no pushes to main" to stderr. In the test the message appears, yet the push still runs and lands on the remote. The hook must block the call, and it must still let a normal edit through. What change makes the hook block the call?

      1. ARemove the hook, because a permission rule alone is enough and the hook adds nothing.
      2. BPrint the message to stdout instead, so that Claude reads it before the call runs.
      3. CMove the hook to the user settings, so that it runs for the developer who is pushing.
      4. DExit with code 2 on a push to main, and with code 0 for every other call.
      Show the answer

      Answer: D

      • A A prefix rule misses a push of HEAD:main or a flag between the words. The hook is the second layer, and the bug here is its exit code.
      • B Where the message goes does not block anything. Only the exit code decides whether the call runs.
      • C A user setting can be edited by the developer, and the problem is not where the hook lives.
      • D Correct. Exit code 2 blocks the call, and the reason on stderr goes back to Claude. Code 0 lets a normal edit run.

      • Block at the point of the call: a deny rule for the prefix, and a hook that exits with 2 for the shapes a prefix misses.

      You can now enforce a rule that a team cannot override, and show that the rollout helped.
