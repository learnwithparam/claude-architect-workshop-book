      Prompt layers and caching

      Stable layers first, then cache the prefix

      A timestamp sits on the first line of the Lumen Supply system prompt, so the prefix changes on every call and the cache never hits. The 7,100-token prefix is billed in full on each call, and every team's tenant text is mixed into it. This lesson orders the layers so the second call reads the prefix from the cache. The prompt has three stable layers and one volatile turn. The policy layer is the shop's rules, shared by every team. The tenant layer is one team's tone, and the guardrail layer holds the limits on every reply. The turn is the question and the time it was sent.

      I doWatch the failure and its fix.

      One prefix, many calls

      The model reads all the layers, the API caches the stable ones, and your code decides their order. A cache hit needs the start of the prompt to be identical, byte for byte, up to a marker you place.

      Three things go wrong, in this order. A timestamp at the top changes the prefix on every call. There is no cache marker, so nothing is reused even when the prefix is stable. And tenant text is mixed into the policy, so one edit changes the start of the prompt.

      The second call reads from the cache

      Two calls ask different questions with the same prefix. The first call writes 7,113 tokens to the cache and reads none. The second reads all 7,113 back and sends only 33 fresh tokens.

      Cached tokens still fill the context window. A cache lowers the price of the prefix, not its size, so the prefix, the history and the reply must still fit together.

      Open a card to see the usage fields behind each call. A cache write costs 1.25 times a fresh input token, and a read costs a tenth of one. Ten thousand calls like the second cost $9.89 on Haiku. The prices are this lab's figures.

      The layer order, written as code

      build takes the three layers and the turn, and returns the system prompt and the messages. Stable text goes first, the turn goes last, and one cache marker follows the guardrail.

      The marker cannot sit inside text that changes. A conversation's earlier messages change on every turn, so they go in the messages after the marker, never in the system layers. The prefix must also reach a minimum size before the API will cache it, which is 4,096 tokens for this model. Below that, a marker is ignored without an error.

      Policy, tenant, guardrail, then the turn

      The time moves to the end, inside the turn. The three layers become separate blocks in order, and one marker follows the guardrail. Each tenant's text stays in its own layer, so an edit to it changes that layer and leaves the policy block unchanged.

      With one marker, each team's cached prefix includes its own tenant text, so the teams do not share a cache.

      The first call now pays a write of 7,113 tokens. Every later call reads them for a tenth of the price, so 10,000 calls cost $9.89 and not $73.92.

      The stable layer as a Skill

      A prompt that a whole team pastes drifts, because each copy is edited on its own. A Skill is one file the team loads, so the stable rules live in one place. Its body holds only text that does not change, which is the rule of the cached prefix: no time and no tenant name.

      Its description says when to use it. A session loads the Skill by that description, so a vague one means the Skill is skipped.

      The Messages API calls above do not load a Skill, so the Skill is a separate file. The checks grade SKILL.md in the same work folder, and Enforce in managed settings and hooks ships a skill to every team.

      SKILL.mdgreen lines are what the fix adds

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. A support agent sends a 7,000-token system prompt 10,000 times a day, and the usage field cache_read_input_tokens is zero on every call. The prompt has a cache marker after its last rule, the first line holds the current time, and the cost report shows the prefix billed in full. What should the team do first?

      1. ARaise max_tokens so the cache has room to store the prefix between the calls.
      2. BAdd a second cache marker at the top of the prompt, so the time line is cached as well.
      3. CMove the text that changes on every call to the end, then read the usage again.
      4. DWait a day, because a cache needs many calls before it starts to return reads.
      Show the answer

      Answer: C

      • A max_tokens limits the reply, not the cache. Raising it changes nothing about the prefix.
      • B A marker caches the text before it, and that text still changes on every call, so a second marker never matches.
      • C Correct. A hit needs an identical prefix. The time on the first line changes it every call, so it moves after the marker.
      • D A cache hit does not depend on call volume. A prefix that differs each call never hits, however long you wait.

      2. The system prompt starts with the time of the request, and the compliance team wants it kept for audits. The prompt is 7,000 tokens long, 10,000 calls a day share the rest of it, and the cost report shows no cache reads. Both the audit record and the cost target must be met. What is the right change?

      1. ADelete the time, because audit records are not the prompt's job and cost comes first.
      2. BKeep the time, but send it after the marker with the turn, and log it from your code.
      3. CKeep the time on the first line and add a cache marker right after it, so it is cached.
      4. DRound the time to the nearest hour so the prefix changes less often than it does now.
      Show the answer

      Answer: B

      • A The audit need is real and can be met without the prompt. Deleting it drops a requirement.
      • B Correct. The time stays in the request, after the cached layers, so the prefix is identical while the audit still has the value.
      • C A marker after the time caches a prefix that starts with a changing line, so it still never matches.
      • D A prefix that changes every hour still misses on the first call of each hour, and it blurs the audit time.

      3. Three teams share a 7,000-token policy and differ only in a short tone paragraph, and each team edits its tone about once a week. The tone paragraph now sits first in one block, above the policy. The layout must keep each edit inside that team's own text and leave the shared policy text untouched. How should the prompt be laid out?

      1. AGive each team its own full copy of the prompt, so one team's edit cannot reach another team.
      2. BKeep one block and cache each team's prompt for longer, so a weekly edit is covered by the cache lifetime.
      3. CKeep one block with the tone paragraph moved to the end and no marker, so the edit sits last.
      4. DPolicy, tenant and guardrail as separate layers, in that order, so an edit changes only the tenant layer.
      Show the answer

      Answer: D

      • A Copies drift, and each copy is still one block with the tenant text mixed into the policy.
      • B An edit makes a new prefix whatever the cache lifetime is, and the policy is still mixed with the tone paragraph.
      • C Without a marker nothing is cached, and the policy and the tone paragraph still share one block.
      • D Correct. Each layer has one owner and one rate of change, so a tone edit changes the tenant layer and the policy block stays as it was.

      4. A review of a cost report asks what must be true for a cached prompt to be read back. The system prompt is 7,000 tokens and the marker is placed after its last stable layer. The model has a minimum cacheable size. Select two facts that the team should rely on.

      1. AA longer prompt caches better, so padding the prefix raises the hit rate.
      2. BOnce a marker is set, every later call reads from the cache, whatever the prefix holds.
      3. CThe prefix up to the marker must match the earlier call exactly.
      4. DThe prefix must reach the model's minimum size, or the marker is ignored.
      Show the answer

      Answer: C, D

      • A Length helps only up to the point where the prefix is cacheable. Padding adds cost and does not change whether text matches.
      • B A read depends on a matching prefix and on the entry still being live. A marker alone guarantees nothing.
      • C Correct. One changed character before the marker is a different prefix and a miss.
      • D Correct. Below the minimum, the API ignores the marker and no error is raised.

      1. APut it in one Skill the team loads, with a description that says when to use it.
      2. BAsk each engineer to re-paste the newest copy every Monday from the chat history.
      3. CCache the pasted prompt so every session sees the same text for the whole week.
      4. DMake the prompt longer so it covers every case and no engineer needs to edit it.
      Show the answer

      Answer: A

      • A Correct. One file is the home of the rule, the whole team loads it, and a change is made once.
      • B Re-pasting relies on memory and still leaves eight copies that can differ by Tuesday.
      • C A cache saves cost on a repeated prefix. It does not decide which text a session starts with.
      • D A longer prompt is a longer copy to drift, and it still needs edits.

      9. A team marks a 150,000-token document as a cached prefix on a 200,000-token window and expects the cache to free the space. Each call then adds 40,000 tokens of history and asks for a 20,000-token reply, and long cases fail with a length error. The cost target is already met. What explains the error?

      1. ACached tokens still fill the window, so 150,000 plus 40,000 plus 20,000 is over 200,000 and the input must shrink.
      2. BThe cache read is slower than a fresh read, so the call times out and reports a length error.
      3. CThe reply budget is too low, so raising max_tokens to 40,000 will leave room for the reply.
      4. DA second marker after the document would stop its tokens from counting against the window.
      Show the answer

      Answer: A

      • A Correct. A cache lowers the price of the prefix and not its size. Input and reply share the window, and 210,000 does not fit in 200,000.
      • B A cache read is faster than a fresh read, and a slow call does not produce a length error.
      • C A larger max_tokens asks for a bigger reply, which leaves less room for the input and makes the error more likely.
      • D A marker changes how the prefix is billed. Every token of it is still in the window.

      • D max_tokens limits the reply. It does not decide what the cache keeps.

      Conclusions

      • Put stable layers first and the volatile turn last, so the prefix is the same on every call.
      • Place one cache marker after the last stable layer, and keep the prefix above the minimum size.
      • Read cache_read_input_tokens on the second call to prove the cache hit, and keep shared rules in one Skill.

      You can now order a prompt into layers, place a cache marker, and read the usage fields to prove a hit.

      Prefix

      The start of the prompt, up to the cache marker, which must match exactly to hit

      Cache marker

      The cache_control field that ends the cached prefix

      Cache write

      The first call that stores the prefix, billed at 1.25 times a fresh input token

      Cache read

      A later call that reuses the prefix, billed at a tenth of a fresh token

      Layer

      One block of the system prompt with one owner and one rate of change

      Skill

      One file of reusable instructions that a team loads instead of pasting
