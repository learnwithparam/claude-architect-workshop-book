      Context editing and memory

      Clear old tool results and keep the facts in memory

      A refund case runs for many lookups, and every old result travels with every new request. The request grows past the budget, and the one fact the customer asked about sits in the oldest result. This is the refund desk at Lumen Supply. You will watch a long case overflow, then fix it by clearing old results and keeping the case facts in memory.

      I doWatch the failure and its fix.

      Old results are the bulk of a long request

      Three parts share the work. The API clears old tool results, your code saves the facts, and Claude answers. Compaction, a beta feature that swaps old turns for a summary, is the other server-side way to shrink a request.

      The case is about 40 messages long at Lumen Supply. It holds the refund approval in its first tool result and 18 long shipment scans after it. Every lookup is sent again on every later call.

      A subagent, a second agent started for one job, keeps noisy discovery out of the main context. The main agent coordinates and asks it a specific question, and only a short answer comes back.

      Clear old results, and note the facts first

      Two changes. edits clears old tool results past 3,000 input tokens and keeps the last three. run_command runs the memory commands Claude sends. It refuses any path outside /memories. The memory tool has a sixth command, rename, which this lab leaves out, and its view is simplified to a directory listing or one file.

      The case facts are written to memory first, and the prompt tells Claude to view memory before it answers. Count the input tokens before and after to see the fall. The context edit is a beta setting, sent with the header context-management-2025-06-27. If you want the memory tool's own results kept, exclude_tools lists tools the clear must skip.

      A memory file also works as a scratchpad for a long investigation. Findings written outside the window can be read back exactly, after a clear, after a crash or in a new session. When a run crashes, it continues from the saved state, not from the start.

      The Agent SDK serves memory as a tool

      The memory tool is served by an in-process tool server, and your run_command handles each call. The context edit is an API setting that this SDK run does not use. This is a real Claude Haiku 5.5 run through the SDK. With the starting code the notes cannot be read, and Claude cannot answer.

      Memory is not resume. A resumed session brings back the saved history, where cleared results are gone, while a memory file keeps what your code wrote. See A summary drops the facts unless code keeps them for resume and fork.

      Do not confuse this memory tool with CLAUDE.md, the notes file Claude Code reads at the start of a session.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. A 40-message refund case sends about 8,300 input tokens per request against a 5,000 budget. Eighteen old shipment scans are most of it, and only the last few matter. What is the cleanest fix?

      1. AClear old tool results past a trigger, keeping the latest few.
      2. BTell Claude in the system prompt to ignore the old shipment scans.
      3. CSwitch to a model with a larger window so the whole history fits.
      4. DSummarise the whole case by hand after every turn.
      Show the answer

      Answer: A

      • A Correct. The edit drops stale results from the request, so tokens fall, while recent results stay.
      • B An ignored result is still sent and still billed on every call.
      • C A larger window still pays for the stale scans on every turn.
      • D A hand summary costs a call each time and can drop a fact, where clearing is one setting.

      2. On turn 40 of a case each reply is slower and costs more, though the last question is one short line. What is the cause?

      1. AThe model reads older results more slowly than new ones.
      2. BClaude remembers earlier requests, and that stored work adds up on the server.
      3. CEvery request carries the whole history, so old results are paid again.
      4. DA larger window lowers the cost of each token, and the case has outgrown it.
      Show the answer

      Answer: C

      • A Reading speed is not the cause. Input size is.
      • B The API keeps no memory of earlier requests. Everything the model sees is in the request.
      • C Correct. The history is sent again on each call, so its size is the cost.
      • D A larger window does not lower the cost of the tokens a request carries.

      3. After old results are cleared, Claude cannot say what refund was approved. The 84.50 was only in the first result. What should the design have done?

      1. ATurn off clearing so that no result is ever removed from a case.
      2. BWrite the facts to memory first, then view memory to answer.
      3. CAsk the customer to repeat the amount whenever a result was cleared.
      4. DRaise the clearing trigger until the first result is never cleared.
      Show the answer

      Answer: B

      • A Turning clearing off brings the token cost back.
      • B Correct. Memory sits outside the window, so a cleared result loses nothing that was noted.
      • C Making the customer repeat a fact the system already had is a poor answer.
      • D A higher trigger only delays the clearing, and the fact is lost later.

      4. Select two effects of clearing old tool results past a trigger.

      1. AThe conversation and the customer's question stay in the request.
      2. BThe customer's question is cleared with the results, so Claude must ask again.
      3. CThe API saves each cleared result to a memory file for later.
      4. DInput tokens fall once the trigger fires, and cleared results are gone.
      Show the answer

      Answer: A, D

      • A Correct. Only tool results are cleared, so the conversation and the question stay.
      • B Clearing drops old tool results only. The messages and the question stay.
      • C The API does not save them. Your code writes memory files.
      • D Correct. A long case goes from about 8,300 tokens to about 4,100, and the old results do not come back.

      5. An investigation resumes the next day. Old tool results in the saved history were cleared, and the agent has lost a file path it found on day one. What carries that path across?

      1. AResuming the session, which brings the cleared results back.
      2. BA larger context window, so nothing is ever cleared again.
      3. CA line in CLAUDE.md, which the memory tool writes for you.
      4. DA note saved to memory on day one, read at the start.
      Show the answer

      Answer: D

      • A Resume brings back the saved history. The cleared results are not in it.
      • B A larger window does not bring back what was already cleared.
      • C The memory tool writes files your code stores. CLAUDE.md is a separate file that Claude Code loads.
      • D Correct. Memory is outside the window, so a saved note survives clearing and a new session.

      6. A new session starts tomorrow on the same case, and the notes are in /memories. What should the prompt tell Claude to do first?

      1. ATrust its own recall of the case, which carries over between sessions.
      2. BAsk the customer to restate the case so the notes are not needed.
      3. CView the memory directory, and read the case notes before answering.
      4. DClear every tool result, so the new session starts empty.
      Show the answer

      Answer: C

      • A A new session holds no recall of the old one. Only files your code stored remain.
      • B This repeats work the system already holds and puts the burden on the customer.
      • C Correct. Claude carries nothing over by itself, so the notes are its only record of the case.
      • D Clearing drops tool results and does not bring the case back.

      7. A note in memory says the refund was 84.50. The order record has since changed to 94.50. What should the agent do when it sees the mismatch?

      1. AEdit the note to match the order record, then answer.
      2. BTrust the note, because memory is always right.
      3. CDelete the whole memory directory and start the case again.
      4. DRaise the clearing trigger so the old note is dropped.
      Show the answer

      Answer: A

      • A Correct. The record is the source, and the note is edited to match it.
      • B A note is a copy. It goes stale when the record changes.
      • C This throws away every other fact that is still true.
      • D The trigger clears tool results, and a memory file is not one.

      8. Select two rules that keep a memory tool handler safe.

      1. ALet Claude pick any absolute path, for flexibility.
      2. BRefuse any path outside /memories.
      3. CReturn an error string for a command it cannot run, so Claude can correct itself.
      4. DDelete the memory files after each answer, so storage stays small.
      Show the answer

      Answer: B, C

      • A An open path lets a bad command read or write files outside the case.
      • B Correct. Claude's paths are untrusted input, so the handler checks them.
      • C Correct. An error string goes back as the result, and Claude can retry or choose another command.
      • D Deleting the files loses the facts the next call needs.

      9. Claude sends a memory tool command to create a file. What runs it?

      1. AThe API, which keeps the memory files on Anthropic servers.
      2. BClaude itself, which writes the file during the reply.
      3. CThe CLAUDE.md file, which Claude Code updates on each command.
      4. DYour application code, which applies the command to storage.
      Show the answer

      Answer: D

      • A The API does not store the files. Your code does.
      • B Claude only sends the command. It cannot write to your storage.
      • C CLAUDE.md is a file Claude Code loads. It is not the memory tool.
      • D Correct. The memory tool is client side. Claude asks, and your code decides what is stored and where.

      10. A long investigation drifts into generic answers about typical patterns, and the specific findings from 25 turns ago are gone from the request. What should the agent do?

      1. ARaise the output token limit so replies can name more detail.
      2. BWrite key findings to a scratchpad file, and read them back.
      3. CSwitch to a model with a larger window.
      4. DTell the model in the system prompt to be specific.
      Show the answer

      Answer: B

      • A The output limit controls reply length, and the findings are missing from the input.
      • B Correct. A file outside the window holds the findings, so they can be read back exactly.
      • C A larger window holds more, but the findings are still buried or cleared.
      • D A prompt cannot bring back detail that is no longer in the request.

      11. A long run crashes at turn 30 of 40. What lets it continue instead of starting over?

      1. AResume, which brings back every cleared result.
      2. BA longer prompt that explains what the run was doing.
      3. CSaved structured state that the run reads back on restart.
      4. DA larger window, so that the crash does not happen again.
      Show the answer

      Answer: C

      • A Resume restores saved history, and results cleared earlier are not in it.
      • B A prompt from memory repeats what the agent thought, and misses what it found.
      • C Correct. State saved outside the window, such as the facts so far, lets the run pick up again.
      • D A larger window does not stop a crash, and saves nothing for the restart.

      12. Select two good uses of a subagent in a long investigation.

      1. AGive it the whole history, so it can decide what matters.
      2. BAsk it one specific question, and take back a short answer.
      3. CHave it return every raw result, so the main agent sees everything.
      4. DKeep coordination in the main agent, discovery in the subagent.
      Show the answer

      Answer: B, D

      • A A subagent with the whole history brings the same bulk into a second window.
      • B Correct. A specific question with a short return keeps the noise out of the main context.
      • C Raw results return the bulk to the main agent, which defeats the point.
      • D Correct. The main agent coordinates, and the subagent's detail stays in its own context.

      Conclusions

      • Old tool results are the bulk of a long request. Clear them past a trigger and keep the latest few.
      • A cleared result is gone. Any fact you need later goes to memory first.
      • The memory tool is client side. Claude sends a command and your code decides what is stored.
