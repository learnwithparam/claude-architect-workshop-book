      Tool descriptions

      The description decides which tool Claude picks

      Your agent has four tools, and three of them say "Gets order info". A customer asks about an old order, and Claude picks the tool that only knows recent ones. The lookup finds nothing. This is the agent at Lumen Supply, an online electronics shop. You will watch the wrong tool answer, then fix it with four better descriptions.

      I doWatch the failure and its fix.

      Claude sees only a name and a description

      The Lumen Supply agent has four tools. One looks up recent orders, one finds older orders, one lists orders by email, and one tracks a shipment. Claude never sees the code behind them.

      Claude sees each tool's name, its description and its input schema, and nothing else. The input schema lists the fields a tool takes.

      The harness is the code around Claude that runs each tool. Claude picks the tool, the harness runs it, and no code checks the pick. The description is the only place to say what a tool is for.

      Three tools that say the same thing

      Three of the four descriptions read "Gets order info". Nothing says which orders each tool covers or what to pass in. A description that reads like a label gives Claude nothing to choose with.

      Every tool is sent on every request, so each one costs input tokens and adds a choice. A long list of tools lowers accuracy. The fix here keeps four tools and makes them distinct.

      The same idea holds for bigger agents. One agent with 18 tools, where each role needs about 4, picks wrong more often, so give each role only the tools it needs. A subagent is a second agent started for one job. If it inherits every tool, it can call process_refund, and a prompt line against it is only a request.

      Descriptions say what goes in and when to use them

      Each precise description gives the input, what comes back, when to use the tool and which tool to use instead. The boundary is a number: 90 days.

      A catch-all tool is better split into narrow ones with clear contracts. Rename a tool only after its description is fixed, because the description is what Claude reads.

      Descriptions steer the choice. The tool_choice setting forces it. auto is the default and lets Claude answer with no tool. any forces some call, and none forbids calls. A named tool, such as get_customer, forces that one, which a step that must run first needs. This lab sends any.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. Two order tools both say "Gets order info". On 31 of 100 tickets about orders older than 90 days the agent asks the recent-orders tool and answers "not found". What fixes it?

      1. ARaise max_tokens so the model has room to think about which tool to call.
      2. BCut each description to two words so the model has less text to compare.
      3. CSay in each what goes in, which orders it covers and the tool to use instead.
      4. DRetry every "not found" with the other order tool, and keep the descriptions.
      Show the answer

      Answer: C

      • A The pick is one short block of output. The limit was not the cause of the wrong tool.
      • B Shorter text gives the model less to choose with. Two tools with the same two words are still a coin flip.
      • C Correct. The model reads only the description, so the boundary of 90 days has to be written there.
      • D A retry hides the miss and doubles the calls. The next ticket still starts with the wrong tool.

      2. After a rename from lookup_order and find_order to get_order and fetch_order, the same 31 of 100 tickets still go to the wrong tool. The one-line descriptions did not change. What is the cause?

      1. AThe descriptions still say nothing about which orders each tool covers.
      2. BThe new names are still not clear enough, so a third rename with better words should fix it.
      3. CTwo tools are too few, so a third order tool should be added to split the traffic between them.
      4. DThe sampling settings are too loose, so the model picks a different tool on each ticket.
      Show the answer

      Answer: A

      • A Correct. The fix is in the description. Rename after the boundary is written, not instead of it.
      • B Names help a little, but two names with no coverage still leave the choice open. Renaming again repeats the miss.
      • C A third tool with the same kind of description adds one more choice and no more information.
      • D Settings change how varied the pick is, not what the descriptions say.

      3. A system prompt says "call lookup_order for any question about an order". The descriptions still all say "Gets order info". Every order ticket now goes to lookup_order, and 38 of 100 are old orders that fail. What is the right fix?

      1. AAdd a routing line for each ticket type that has failed so far, one by one.
      2. BAdd a prompt line that names find_order for old orders, so the descriptions can stay vague.
      3. CSwitch to a larger model, which reads the system prompt more carefully.
      4. DWrite the coverage and the neighbour into each description, and drop the routing line.
      Show the answer

      Answer: D

      • A A list of ticket types grows with every miss, and the next new ticket type fails again.
      • B This ties the tool boundary to one prompt. Any other prompt or subagent that uses these tools gets no routing and misses again.
      • C A larger model still cannot read coverage that nobody wrote into the descriptions.
      • D Correct. A lean in the prompt only matters because the descriptions do not separate the tools. Fix them first.

      4. Select two things a good tool description states.

      1. AThe code that the tool runs, so the model can read how it works.
      2. BWhat the tool takes as input and what it returns.
      3. CThe pass rate the tool had in last month's evaluation.
      4. DWhen to use the tool, and which neighbouring tool to use instead.
      Show the answer

      Answer: B, D

      • A The model never sees the code. It sees the name, the description and the input schema.
      • B Correct. Inputs and outputs tell the model what to send and what to expect back.
      • C A pass rate is for the team that runs the evaluation. It does not help the model pick a tool.
      • D Correct. The boundary with the neighbour is what keeps two similar tools apart.

      5. One agent holds 18 tools and picks the wrong one on 1 in 5 tickets. Each role uses about 4 of them. What is the fix?

      1. AAdd six more tools, so every ticket type has a tool made for it.
      2. BGive each agent only the few tools its role needs.
      3. CKeep one list for everyone, because one list is simpler to maintain.
      4. DPut a paragraph in the prompt that says which tool suits which ticket.
      Show the answer

      Answer: B

      • A More tools mean more choices and more tokens on every request, and accuracy falls as the list grows.
      • B Correct. A short list per role leaves few tools to confuse, and each tool reads as distinct.
      • C Maintenance is easier, but the miss rate is the cost, and it lands on customers.
      • D A paragraph of routing is a patch for a list that is too long. It also costs tokens on every call.

      6. A research subagent called process_refund twice in 50 runs. The tool was in its list because every subagent gets the parent's tools. What should change?

      1. AKeep the shared list, because two calls in 50 runs is a rate the team can accept.
      2. BMove the subagent to a larger model that follows the prompt better.
      3. CGive the subagent only the read tools its research needs.
      4. DAdd a line to its prompt that says never to call process_refund.
      Show the answer

      Answer: C

      • A Two refunds moved by a research agent is not an acceptable rate. Removing the tool makes it zero.
      • B A larger model may miss less often, but the tool is still there to be called.
      • C Correct. A tool the subagent cannot see cannot be misused.
      • D A prompt rule is a request. It lowers the rate, and two misses in 50 runs are still money moved.

      7. A step in the agent must run get_customer first on every ticket. Which tool_choice setting does that?

      1. A{"type": "auto"}, because the model always calls a lookup first.
      2. B{"type": "tool", "name": "get_customer"}, which forces that tool.
      3. C{"type": "any"}, which forces the model to call get_customer.
      4. DA prompt line that says to call get_customer first, with auto left on.
      Show the answer

      Answer: B

      • A With auto the model may answer without a tool, and it may pick a different one.
      • B Correct. A named tool forces that tool on this request.
      • C any forces some tool call, but the model chooses which. It may call another tool first.
      • D A prompt line makes the call likely, not certain. A step that must run needs the setting.

      8. Select two valid values for the type of tool_choice.

      1. Aauto, where the model chooses on its own whether a tool is needed.
      2. Ball, where the model calls every tool once.
      3. Csequential, where the tools run in the order they are listed.
      4. Dany, where the model must call some tool.
      Show the answer

      Answer: A, D

      • A Correct. auto is the default, and the model may answer without a tool.
      • B There is no such setting. The model calls the tools it needs, not every tool.
      • C There is no such setting. Order comes from the model's turns, not from the list.
      • D Correct. any forces a call, and the model picks which tool.

      Conclusions

      • The description is how Claude chooses a tool. It is the interface, not a comment.
      • A good description gives the input, the output, when to use it and which neighbour to use instead.
      • Tool choice is testable: run tickets, count the right picks, fix the words.
