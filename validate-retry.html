      Validate and retry

      Retry with the exact error, and only when a retry can help

      The invoice extractor fails a record, asks again, and asks again. One invoice has a date in the wrong form, and another has no date at all. Only one of them is worth a second call. This is the extractor at Lumen Supply, an online electronics shop. You will watch a blind retry lose a good record, then write a validator that decides when another call can help.

      The validator decides whether another call can help

      Claude fills in an invoice record through a tool. A validator checks the record against what the ledger accepts. When the record fails, the validator has to decide what happens next.

      Three things go wrong in turn. With no retry, invalid output ends the run. A blind retry that sends only "Try again" loses the record. A retry on absent data has nothing to fix.

      The starting retry says try again

      The starting validator retries every error, and the retry is two words. It does not say what failed, and it does not even repeat the invoice.

      It also cannot tell a value that is wrong from a value that is not there.

      A good retry names the field and the error, shows the failed record, and puts the invoice text in front of the model again. You will write that retry in the fix below.

      Name the error, then retry only what can change

      The validator now sorts each error. A date that is null and never mentioned in the document is absent. A value that is there but written wrong is a format error.

      Only a format error is retried, once, and the retry carries the document, the failed record and the exact error. Absent data stays null and is flagged for a human to review.

      Refining code with a model follows the same rule: give it information, not pressure. Add an input and expected output example for each shape that fails. Write tests first for requirements you can check, and iterate on their failures. When the requirement is unclear, ask the model to interview you before it writes code.

      When a reply stops at max_tokens

      A long invoice can use up the token limit before the record is finished. This loop starts every call with a limit of 100 tokens, small on purpose, so the long invoice shows the cut-off. The reply stops at max_tokens, and the record arrives with its last fields missing. The starting loop accepts it.

      Switch to the retry with more room. The validator sees the stop reason, asks once more with a larger limit, and every field arrives. A prefill starts the reply for the model and keeps a plain-text answer in shape, though newer large models reject one. This loop forces a tool, so it raises the limit instead.

      This part is interactive in the lab: run ./workshop watch validate-retry.

      Try it: retries and invoices

      Change one setting at a time. With no retry, the first invalid record ends the run. With a blind retry, the second call loses the record. With the exact error, the date is fixed, and an absent date is flagged after one call.

      Every combination is a recorded run, so this works with no internet. A schema cannot tell a missing date from a badly written one. The validator can.

      A schema checks shape only. It cannot tell a true value from a wrong one of the right form, and it cannot fill a fact the document lacks. Code checks a value against its source. Force the tool so a record always arrives, and make a field nullable when the source may lack it.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. A due date written as "3rd of September 2026" fails validation on 12 of 200 invoices. The value is on the page, only in the wrong form. What is the best response?

      1. ADrop due_date from the required fields, so those records pass.
      2. BSend the same request again, since output varies between runs.
      3. CRetry once with the document, the failed record and the exact error.
      4. DRaise the retry limit to five, so the same request gets more chances.
      Show the answer

      Answer: C

      • A Dropping the field hides the failure, and the ledger loses a date it could have had.
      • B An identical request has the same odds of the same mistake. Nothing tells the model what was wrong.
      • C Correct. The fact is in the document, so one retry with the exact error can fix the form.
      • D More attempts of a request that does not mention the error only repeat the error.

      2. 20 invoices in a batch state no due date. The loop retries each one 5 times and then fails. What should the loop do instead?

      1. AKeep the date null and flag the invoice for a person after the first call.
      2. BRetry until a date appears, since every invoice has one somewhere.
      3. CRetry with the exact error each time, so the message eventually gets through.
      4. DRemove due_date from the record, so the validator stops complaining.
      Show the answer

      Answer: A

      • A Correct. The document has no date to find, so a retry cannot help and a person has to decide.
      • B Not every invoice has a date, and a loop that waits for one will eventually get an invented one.
      • C A clear error message does not add a fact the document lacks.
      • D The ledger needs to know the date is missing. Removing the field loses that.

      3. The retry message is "Try again." and the same error comes back on 9 of 10 retried records. What change fixes it?

      1. AAllow more retries per record, so one of them gets it right.
      2. BKeep the message short, since the error text only adds noise.
      3. CRaise the temperature, so the second reply differs from the first.
      4. DSend the document, the failed output and the specific error.
      Show the answer

      Answer: D

      • A Each extra attempt carries the same two words, so it has the same odds.
      • B The error text is the information the model needs to change anything.
      • C More variety is not aimed at the mistake. It can turn a small error into a different one.
      • D Correct. With the document, the output and the error, the model can see what to change.

      4. Which two items belong in a retry message after a format error? Select two.

      1. AA request that the model tries harder this time.
      2. BThe record that failed validation.
      3. CThe specific validation error, such as the field and what was wrong with it.
      4. DPermission to leave the field out if it is hard to fill.
      Show the answer

      Answer: B, C

      • A Effort is not the problem. The model needs to know what to change.
      • B Correct. The failed record shows the model exactly what it wrote.
      • C Correct. The field and the reason point the retry at the one thing to fix.
      • D Leaving the field out trades a fixable format error for missing data.

      5. On 6 of 300 invoices the record matches the schema, but the total is 1,000 times too large. What catches this?

      1. ATighten the schema until it forbids the wrong number.
      2. BA check in code that compares the value with what the document says.
      3. CRetry every record once to be safe.
      4. DForce the tool, so the values are checked by the API.
      Show the answer

      Answer: B

      • A A schema says what shapes are allowed. A wrong number of the right shape passes it.
      • B Correct. A value is checked against its source by code that knows what the source says.
      • C A blind retry on every record doubles the cost and may produce the same wrong number.
      • D Forcing the tool fixes the shape of the reply. It has no say over what the values mean.

      6. 5 of 100 replies arrive as prose, and the ledger needs a record every time. What should change?

      1. ARetry the prose replies until one of them holds a record.
      2. BPull the fields out of the prose with a regular expression.
      3. CRun the validator on the prose, so it rejects anything that is not a record.
      4. DSet tool_choice to the extraction tool, so a record always arrives.
      Show the answer

      Answer: D

      • A Each retry may answer in prose again, and each costs a call.
      • B Prose changes wording from run to run, so a pattern breaks on the first new phrasing.
      • C A validator rejects prose. It cannot turn it into a record.
      • D Correct. A named tool makes the reply the tool's input, in the shape of the schema.

      7. Invented values appear in 15 of 100 records, all in a field the source often lacks. What is the fix at the source?

      1. AMake the field nullable, so silence has a place to go.
      2. BRetry each invented value until one passes validation.
      3. CKeep the field required and add a pattern that checks its form.
      4. DAsk for the field again with the exact error, so the model finds it.
      Show the answer

      Answer: A

      • A Correct. When the source may lack a fact, the honest answer has to fit the schema.
      • B The next value to pass validation is another invention that looks right.
      • C A pattern checks form. A made-up value of the right form passes.
      • D An error message cannot add a fact the document lacks.

      8. Which two things can a schema not do? Select two.

      1. ATell whether a value in the right form is the true one.
      2. BReject a record whose total arrives as a string.
      3. CRequire that a due_date field is present in the record.
      4. DFill in a fact that the document never states.
      Show the answer

      Answer: A, D

      • A Correct. The schema checks the shape, so a wrong date in the right shape passes.
      • B A schema can do this. A type check is exactly what it enforces, so a string total fails.
      • C A schema can do this. A required field is part of the shape it checks.
      • D Correct. A schema describes what is allowed and adds no information.

      9. A first fix for a date parser fails on 3 input shapes, and the description of the goal did not help. What do you add next?

      1. ARepeat the goal in capital letters at the top.
      2. BSend the same message again until a run passes.
      3. CAn input and expected output example for each shape.
      4. DA higher limit on attempts, from 2 to 6.
      Show the answer

      Answer: C

      • A Capital letters add emphasis, not information about the three shapes.
      • B The same message leaves the same gap, so runs repeat the same fix.
      • C Correct. Examples show the model what each shape looks like and what it should become.
      • D More attempts on a request that lacks the examples repeat the miss.

      10. A change has 4 requirements, each easy to check. How do you build it so that progress is visible?

      1. AWrite the code first and add tests at the end.
      2. BWrite the tests first, run them, and iterate on their failures.
      3. CDescribe the tests in prose and skip running them.
      4. DDelete any failing test that the first version cannot pass.
      Show the answer

      Answer: B

      • A Tests written last check what the code happens to do, not what was wanted.
      • B Correct. Failing tests state the target, and each run shows what is left.
      • C A test that never runs says nothing about the code.
      • D A deleted test stops checking the requirement it stood for.

      11. The requirement for a report is unclear, and the model has guessed wrong 3 times. What helps most?

      1. ASend the same request again until a guess is right.
      2. BPick the most likely guess and ship it.
      3. CWrite a longer request that lists every detail you can think of.
      4. DAsk the model to interview you with questions before it writes code.
      Show the answer

      Answer: D

      • A Each guess comes from the same missing information.
      • B A guess shipped is a guess that the users find.
      • C A longer list of details still misses the ones you did not think of.
      • D Correct. Questions bring out the requirements that nobody had written down.

      12. Which two things make a refinement request work better? Select two.

      1. AExamples of the output you want.
      2. BThe same request with more emphasis.
      3. CA failing test to iterate against.
      4. DLeaving out the error text, so the model is not anchored on it.

      Answer: A, C

      • A Correct. An example shows the target in a way a description cannot.
      • B Emphasis raises the stakes without adding information.
      • C Correct. A failing test says what is wrong and tells you when it is fixed.
      • D The error text is what the model needs, and leaving it out removes the signal.

      Conclusions

      • Validate the output, and retry with the exact error only when a retry can help.
      • A format error is worth one retry. Absent data stays null and is flagged for a human.
      • A reply cut off at max_tokens is retried once with more room.
