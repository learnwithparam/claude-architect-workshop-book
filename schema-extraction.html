      Schema extraction

      A nullable schema and a forced tool make extraction trustworthy

      Lumen Supply reads supplier invoices into its ledger. One vendor never prints a PO number, the schema demands one, and the model writes a value nobody wrote. You will watch that happen, then fix it. This is the extractor at Lumen Supply, an online electronics shop. The schema is the contract, and you will change what it allows.

      I doWatch the failure and its fix.

      The schema is the contract Claude writes to

      The extractor gives Claude one tool. The tool's input schema is the shape of the record the ledger wants. Claude fills the tool in, and the ledger checks the result.

      Three things go wrong in turn. The answer is free text that code cannot parse. A required field the invoice lacks gets a made-up value. A category list with no place for an odd invoice files it wrongly.

      A clean invoice becomes a valid record

      A supplier invoice goes in and a record comes out, with vendor, total, PO number and category. Open a card to see the data each side saw.

      This works because every field is printed on the invoice. The harder cases are invoices that are silent about something.

      The starting schema demands a value for everything

      Every field is required, the tool choice is auto (Claude may answer in text instead of calling the tool), and the category list has no escape. Each of those is a reasonable default, and each one fails on a real invoice.

      A field that is required when the source may lack it leaves Claude only one way to comply: write something.

      The record holds a guess, or never arrives

      With tool_choice on auto, Claude called the tool and wrote an empty string for the PO number. The schema accepts an empty string, so the ledger got a valid record that is not null.

      Auto also lets Claude answer in text: on the odd invoice it replied in prose and the ledger got no record at all. Try forcing the tool, and Claude has to fill the field.

      Forcing the tool kept the shape and still broke the value: the PO number became the placeholder <UNKNOWN>. A forced tool guarantees a record. It does not make the values true.

      Force the tool, allow null, keep an escape

      Three changes. The tool is forced, so a record always arrives. The PO number may be null, so silence on the invoice has somewhere to go. The category list ends with other and a detail field, so an odd invoice is not misfiled.

      Vendor and total stay required, because every invoice has them. Those changes fill schema() and choice(), in that order: nullable PO number and other first, then the forced tool. The third stub, examples(), is filled in the examples step below.

      tool_choice takes four values: auto, any, a named tool and none. A named tool forces that tool, which suits a first step that must be an extraction. Claude Haiku 5.5 accepts a forced tool. Some larger current models reject it with a 400 error, and there a structured output format (output_config.format) returns the record.

      Examples settle what a schema cannot

      Some invoices print the PO number as a bare number, and the ledger wants the PO- form. A schema cannot say that. Worked examples of differently laid-out invoices can, and examples() returns them.

      Switch between no examples and the examples. Without them the model copies the number as printed. With them it writes the form the ledger expects.

      An example can also settle a name written three ways, with a one-line reason.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. 40 of 800 weekly invoices reach the ledger with the PO number PO-0000. The vendor behind them prints no PO number at all. What is the fix at the source?

      1. AAdd a prompt line that tells the model not to invent a PO number.
      2. BLet po_number be null in the schema, so silence has a place to go.
      3. CReject every record whose PO number is PO-0000 after extraction.
      4. DKeep the field required, and add a regex that checks the PO format.
      Show the answer

      Answer: B

      • A A prompt line asks politely, while the schema still demands a value. The model has to comply with one of the two.
      • B Correct. A field the source may lack is nullable, so the honest answer fits the schema.
      • C This filters one placeholder. The model will write another one, such as N/A or 0.
      • D A format check cannot tell a real PO number from a made-up one that looks right.

      2. The extractor offers its tool with tool_choice set to auto. In 5 of 100 runs the reply is prose that the ledger cannot parse. What should change?

      1. AWrite a longer system prompt that insists on a tool call.
      2. BRetry any prose reply until a tool call comes back.
      3. CPull the JSON out of the prose with a regular expression.
      4. DSet tool_choice to the extraction tool, so a record always arrives.
      Show the answer

      Answer: D

      • A Insisting is still a request. On auto the model may choose prose on any run.
      • B Retries hide the cause and cost a call each time. The next prose reply is only a matter of time.
      • C Prose has no stable layout, so a pattern breaks on the first reply that is worded differently.
      • D Correct. A named tool in tool_choice turns the reply into tool input that follows the schema.

      3. A category list has six values. Each week 30 invoices for event hire land under freight, since nothing else fits. What is the change?

      1. AAdd an other value and a category_detail field that says what the item is.
      2. BMake category optional, so the model can leave it empty.
      3. CAdd ten more categories until every invoice seen so far fits.
      4. DTell the model in the prompt to pick the closest category.
      Show the answer

      Answer: A

      • A Correct. An escape value keeps the odd invoice out of a wrong category, and the detail keeps what it was.
      • B An empty category hides the problem from the ledger and loses the information.
      • C A longer list still has an end. The next odd invoice will not fit, and there is nowhere for it.
      • D Closest is how the misfiling happens. The record looks fine and is wrong.

      4. Which two statements about extraction with a tool schema are true? Select two.

      1. AA record can match the schema and still hold a value the invoice does not contain.
      2. BA record that matches the schema holds values that match the invoice.
      3. CA forced tool means the reply is a record rather than prose.
      4. DA forced tool corrects wrong values in fields the invoice cannot fill.
      Show the answer

      Answer: A, C

      • A Correct. The schema checks the shape. A placeholder in a string field is valid.
      • B Shape and meaning are different checks. The schema only does the first.
      • C Correct. With a named tool the model has to reply with that tool's input.
      • D Forcing makes the model fill the field, which is when an invented value appears.

      5. Totals are wrong on 12 of 100 scanned invoices. The total sits in a different place on each layout. What helps most?

      1. ALower the temperature to zero so the model reads more carefully.
      2. BAdd a regular expression that finds the word Total in the text.
      3. CShow examples of invoices with the total in different places.
      4. DShow one example of a typical invoice with the total at the bottom.
      Show the answer

      Answer: C

      • A Temperature changes variety, not whether a layout is understood.
      • B A pattern tied to one word breaks on a layout that says Amount due or puts the figure in a table.
      • C Correct. Examples of differing layouts show the model where the value hides.
      • D One layout teaches one place to look. The others stay as wrong as before.

      6. Across 5 invoice layouts the PO number comes out as 5530, PO5530 or PO-5530. The ledger wants PO-5530. What settles the format?

      1. AWrite a cleanup rule for each of the five layouts after extraction.
      2. BShow examples whose records write the number in the PO- form.
      3. CMake po_number required, so it is always filled in the same way.
      4. DForce the tool, so the format is fixed by the tool choice.
      Show the answer

      Answer: B

      • A Five rules grow to six with the next layout, and each is code to keep.
      • B Correct. An example shows the target form once, and the model carries it across layouts.
      • C Required says the field must exist. It says nothing about how the value is written.
      • D Forcing settles the shape of the reply. The form of a string is not part of it.

      7. One vendor appears as Harlow & Pike, Harlow and Pike Ltd, and H&P. The ledger wants one name. What gives the most consistent result?

      1. ATurn vendor into an enum of every name seen so far.
      2. BAdd a prompt line asking the model to be consistent.
      3. CMerge the names with a regular expression after extraction.
      4. DShow an example that maps the short form to the full name, with a one-line reason.
      Show the answer

      Answer: D

      • A A new vendor has no place in a closed list, and the model misfiles it into the nearest name.
      • B Consistent with what? The model has no way to know which form the ledger prefers.
      • C A pattern merges the names someone thought of. The next variant slips through.
      • D Correct. An example that settles the ambiguity, with its reason, carries to similar names.

      8. Which two effects do worked examples have on extraction? Select two.

      1. AThey let the model call tools that have no schema.
      2. BThe format of a record becomes the same from one run to the next.
      3. CEvery layout is handled, including layouts that were not shown.
      4. DInvented values are less likely on layouts close to the ones shown.
      Show the answer

      Answer: B, D

      • A Tools come from the request. Examples only show inputs and outputs.
      • B Correct. A shown format is the one the model copies.
      • C Examples cover the layouts they resemble. A new layout is still a risk.
      • D Correct. Seeing where values sit on a layout cuts the guessing on similar ones.

      9. A pipeline has three tools, and the first call must be extract_invoice. Some runs open with a different tool. What guarantees the order?

      1. ASet tool_choice to the extract_invoice tool for the first request.
      2. BWrite the first step in capital letters in the system prompt.
      3. CSet tool_choice to any, so a tool is always called first.
      4. DCheck the first call in code and rerun the request when it is wrong.
      Show the answer

      Answer: A

      • A Correct. Naming the tool forces that tool on the first turn, and later turns can go back to auto.
      • B Capital letters are emphasis, which is still a request.
      • C Any guarantees some tool is called. It may be the wrong one.
      • D A rerun costs another call and does not stop the next wrong opening.

      10. A step must call one of three tools, and which one is the model's choice. Some replies are chat instead. What setting fits?

      1. ASet tool_choice to auto, so the model calls a tool when it needs to.
      2. BName one tool, so the model always has a tool to call.
      3. CSet tool_choice to any, so a tool call is required and the model picks.
      4. DSay in the prompt that a tool call is needed on every turn.
      Show the answer

      Answer: C

      • A Auto allows chat, which is the problem.
      • B Naming one tool takes the choice away from the model.
      • C Correct. Any forces a call and leaves the pick of tool to the model.
      • D A prompt line is a request, and the chat replies show it is not always followed.

      11. An assistant has three tools and should answer in text when none of them applies. Which tool_choice fits?

      1. AAny, so the model is sure to use a tool.
      2. BOne named tool, so the model is never without one.
      3. CPut the choice into each tool description instead of the request.
      4. DAuto, so the model decides between a tool and plain text.
      Show the answer

      Answer: D

      • A Any requires a tool call, so a text answer is no longer possible.
      • B A named tool forces that tool on every turn, even when it does not apply.
      • C Descriptions help the model understand a tool. The request decides whether one is required.
      • D Correct. Auto leaves both the tool and the text option open.

      12. Which two statements about tool_choice are true? Select two.

      1. AIt takes auto, any, or the name of one tool.
      2. BWith one named tool, the reply holds that tool's input.
      3. CAuto makes the model call a tool on every turn.
      4. DIt decides which model answers the request.
      Show the answer

      Answer: A, B

      • A Correct. Those are the three forms of the setting.
      • B Correct. A named tool is called, so its input is the answer.
      • C Auto lets the model choose, and a text reply is one of its choices.
      • D The model is set elsewhere in the request. The tool choice only shapes the reply.

      Conclusions

      • A schema fixes the shape of a record. It does not make the values true.
      • A field the source may lack is nullable, and a category list ends with an escape and a detail.
      • Examples settle layouts and formats that a schema cannot express.
