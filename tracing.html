      Tracing

      One run id, one span per call

      The Lumen support agent logs every full prompt with the customer's name and email, and no id ties a run's calls together. When a wrong answer is reported, nobody can find the run, and the log holds data it should not. This is the order status agent at Lumen Supply, an online electronics shop. You will read a log that leaks and cannot find its run, then fix two functions in one file. The fix is a run id, one span per call, and hashed personal fields.

      I doWatch the failure and its fix.

      One wrong answer, twenty minutes to find the run

      The agent answers where an order is. It calls two tools, one for the order and one for its shipping. Each call can leave a record in the log.

      Three things go wrong, in this order. Full prompts are logged with personal data, so the log is a leak. No run id ties the calls of one run together, so a bad answer cannot be found. And alerts fire on single errors, not on a number derived from the spans.

      Span and redact, written as code

      Two functions hold the design. The file shown is the starting one. The span function should write one record per call, with the run id, the name and only the allowed fields.

      The redact function should hash personal data before it is written. The same value should always give the same tag, so a reader can still tell that two spans are about one customer.

      Structured spans with a run id

      span keeps the run id and only the fields in its allow-list. The prompt and the reply are not in it, so they are never written. redact hashes the six personal fields, emails and phone numbers in what remains.

      If a log store that holds personal data leaks, that is a breach to report, and two years of prompts is two years of exposure. Hashing before the write keeps the readable value out of the store. The hash is stable, so the same customer keeps the same tag, and the log still counts as personal data.

      trace.pygreen lines are what the fix adds
      1"""One record per call, tied to its run, with personal data hashed."""23import hashlib4import re56from kit.api import Json78ALLOWED = ("tool", "ms", "status", "error", "turns", "cost_usd", "result")9PERSONAL = "name|email|phone|address|card_last4|birth_date"10FIELD = re.compile(rf'"({PERSONAL})":\s*"([^"]*)"')11EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")12PHONE = re.compile(r"\b\d{3}-\d{4}\b")131415def tag(kind: str, value: str) -> str:16 """A stable stand-in: the same value always gives the same tag."""17 digest = hashlib.sha256(value.encode()).hexdigest()[:8]1819 return f"{kind}#{digest}"202122def redact(text: str) -> str:23 """Hash the personal fields, emails and phone numbers in text."""24 text = FIELD.sub(lambda m: f'"{m[1]}": "{tag(m[1], m[2])}"', text)25 text = EMAIL.sub(lambda m: tag("email", m[0]), text)2627 return PHONE.sub(lambda m: tag("phone", m[0]), text)282930def span(run_id: str, name: str, data: Json) -> Json:31 """One record: the run id, the name and only the allowed fields."""32 kept = {k: data[k] for k in ALLOWED if k in data}33 clean = {34 k: redact(v) if isinstance(v, str) else v for k, v in kept.items()35 }3637 return {"run_id": run_id, "name": name, **clean}

      Triage from a trace

      The runbook has three checks in order: find the run by its id, read the tool spans for errors or slow calls, then read the last model call. Each check has an owner.

      Here the second check finds get_shipping with a carrier timeout, so the fix starts in that tool and not in the prompt. A fault in a tool span is not cured by rewording the prompt. The same spans show the path an agent took, which is the only record of a path that code did not fix in advance.

      Keep the trace useful

      Derived metrics come from the spans, and this slow run shows one. Alert on p95 latency and on the error rate over a window, not on every error. A cost per run that rises while traffic is flat points at a step that grew.

      A trace belongs to its feature. Review the metrics on a schedule, so drift shows up in days. When a feature is retired, retire its span writing and delete the old spans with it.

      Check your understanding

      Answer each question, then read why every option is right or wrong. The wrong options are the mistakes engineers make on the job.

      1. A customer reports a wrong answer from the support agent and gives the time and the order number. The log holds 12,000 prompt lines from that hour, and none carries an id that ties a run's calls together. The on-call engineer has 20 minutes before the next escalation. What should the team add first?

      1. AA run id on every span, made once per run and passed to each call.
      2. BA longer retention period for the prompt lines, so nothing is lost.
      3. CSearch by order number for now, and add run ids when the log grows.
      4. DA second copy of each prompt line in another store.
      Show the answer

      Answer: A

      • A Correct. One id per run lets the engineer pull every span of that run in one query, whatever else is in the hour.
      • B Keeping the lines longer keeps the same 12,000 lines with no way to group them into one run.
      • C An order number can sit in many runs, and waiting means the same 20 minutes on the next report.
      • D A copy of a line with no run id is still a line with no run id.

      2. An agent run writes one giant log line at the end, holding the prompt, every tool result and the reply. A slow run took 9 seconds, and finding which call was slow meant reading a 40 KB line by hand. The team wants the slow call to show up at once. What should it change?

      1. AWrite the line sooner in the run, so the log is fresher.
      2. BPrint the same 40 KB line with line breaks for readability.
      3. CWrite one span per model or tool call, each with its own timing.
      4. DAdd a flag to the line that says the run was slow.
      Show the answer

      Answer: C

      • A A fresher line is still one line, so the slow call stays hidden inside it.
      • B Line breaks make a debug print easier to read. A trace is a set of records that can be queried by call.
      • C Correct. With one span and one timing per call, the slow call is the span with the largest number.
      • D A flag says that a run was slow and not which call was, so the search goes on by hand.

      3. A log store keeps every prompt for two years. A privacy review finds customer emails and phone numbers in 3,400 of the lines. The team may keep the logs for debugging but must stop holding those values in clear text. What is the right change?

      1. ARestrict the log store to two engineers and keep writing the same lines.
      2. BDelete the logs older than one year and keep the newer ones as they are.
      3. CAdd a banner to the log viewer that warns readers about personal data.
      4. DRedact the personal fields before a span is written, with a stable hash.
      Show the answer

      Answer: D

      • A Fewer readers still leaves the data in the store, and a breach of the store exposes it.
      • B The newer logs still hold the values, and the next year of lines will too.
      • C A warning is text for a person. It removes nothing from the store.
      • D Correct. Hashing before the write means the store never holds the value, and the same value keeps the same tag.

      4. A design review lists the fields every span in the order status agent must carry. The team wants any span to be found in one query and read without opening the prompt. Select two fields that every span needs.

      1. AThe run id that ties it to its run.
      2. BThe full prompt, in case a reader needs it.
      3. CThe name of the call and its duration.
      4. DThe customer's email, to find their runs.
      Show the answer

      Answer: A, C

      • A Correct. Without the run id, a span cannot be grouped with the others from the same run.
      • B The prompt holds personal data and is large. A span keeps only the fields it needs.
      • C Correct. The name and the duration say which call it was and how long it took.
      • D An email in a span is personal data. The run id finds the run without it.

      5. An alert pages the on-call engineer on every tool error, and the agent logs about 60 of them a day, mostly short carrier timeouts that retry and succeed. The team now ignores the pages. The goal is fewer pages that still catch a real outage. What fits?

      1. AMute the alert at night, when fewer customers are online.
      2. BSend each error to a chat channel as well as the page.
      3. CPage only when the error rate over a 10-minute window crosses a limit.
      4. DRaise the retry count so fewer errors are logged.
      Show the answer

      Answer: C

      • A Muting at night removes the page when an outage starts at night, and the day noise stays.
      • B A second channel carries the same 60 messages, so it adds noise and fixes nothing.
      • C Correct. A rate over a window comes from the spans, and it fires when errors climb, not when one call retries.
      • D More retries hide the errors in the log while the outage goes on.

      6. After a release, the mean latency of the agent is flat at 1.1 seconds, yet customers say some answers take 10 seconds. The spans show 5 percent of tool calls now take over 8 seconds. The team needs an alert that would have caught this. Which metric should it read from the spans?

      1. AThe p95 latency of the spans, with a limit.
      2. BThe count of runs per hour.
      3. CThe mean latency, with a tighter limit.
      4. DThe size of the log files.
      Show the answer

      Answer: A

      • A Correct. One call in twenty being slow moves p95 while the mean barely moves, and p95 comes from the span timings.
      • B A run count says how busy the agent is. It says nothing about how long a call took.
      • C The mean stays near 1.1 seconds whatever limit is set, because most calls are fast.
      • D Log size grows with traffic and says nothing about how long a call took.

      7. Cost per run rose 40 percent this week, from 0.005 to 0.007 dollars, while traffic stayed flat at 2,000 runs a day. Nothing in the error alerts changed. The team wants to know which step got more expensive. What should it do?

      1. AAsk the model provider for last week's invoice.
      2. BCut the answer length in the prompt and watch the total.

      4. DDerive cost per run from the model spans and compare steps week on week.

      Answer: D

      • A An invoice gives a total for the week. It cannot say which step of which run changed.
      • B A guess changes one thing and may miss the step that grew, such as a third model turn.
      • C A cheaper model may fail the task, and the cost of the step that grew would stay hidden.
      • D Correct. Each model span carries its own cost, so a sum per run and a comparison by step find the change.

      • D A whole hour holds many runs, and the first line is unlikely to be the one that matters.

      • D A review helps the team learn, and it does not tell the engineer on call what to do at 02:00.

      • C Hashing is not optional, and a rush is when a leak is most likely.
      • D Correct. A named owner for each step means a stuck engineer knows who to ask.

      13. A team chose a fixed workflow for an order status feature, then found that the next step depends on what each tool returns. The spans of 50 runs show the path branches in four different ways. The team wants to decide whether an agent fits better. What should it use?

      1. AA vote among the engineers on which design feels cleaner.
      2. BThe prompt length as a measure of how complex the task is.
      3. CThe number of tools the feature holds as a proxy for branching.
      4. DThe spans, to count how often and where the path branches.
      Show the answer

      Answer: D

      • A A vote gives a preference. The spans hold 50 runs of evidence about the path.
      • B A long prompt can drive a fixed path, and a short one can drive a branching path.
      • C Two tools can branch many ways, and ten can run in a fixed order.
      • D Correct. The spans show each call in order, so the branch points can be counted where they happen.

      14. An agent chooses its own tools, so the path it takes cannot be predicted from the code. A customer disputes an answer, and the team must show what the agent did step by step. Only a trace can answer that. What must be true of the trace?

      1. AIt was switched on after the dispute, for the next run.
      2. BIt holds only the final reply, to keep the log small.
      3. CEvery model and tool call is a span under the run id, so the path can be replayed.
      4. DIt holds the prompts in clear text, so the wording is exact.
      Show the answer

      Answer: C

      • A A trace switched on after the dispute has nothing about the run in question.
      • B A final reply says what was answered and not how, so the path is lost.
      • C Correct. With one span per call under one id, the path can be read in order, however the agent chose it.
      • D Clear text adds personal data and is not needed to show the path.

      15. The order status agent has run in production for six months, and its spans are stored and never read. Last week a slow tool went unnoticed for 9 days until a customer complained. The team wants to catch drift sooner. What should it schedule?

      1. AA regular review of the span metrics, such as p95 latency and cost per run.
      2. BA yearly rewrite of the system prompt from scratch.
      3. CA larger log store, so spans can be kept for longer.
      4. DA rule that any engineer may mute alerts they find noisy.
      Show the answer

      Answer: A

      • A Correct. A review of the derived metrics on a schedule shows a slow tool in days, before a customer does.
      • B A rewrite changes the prompt and leaves a slow tool where it was.
      • C Keeping more spans that nobody reads adds cost and does not show drift.
      • D Muting alerts hides drift. It does not look for it.

      16. A feature that used the agent was retired in March, yet its code still writes 15,000 spans a day. The log store grows by 2 GB a week, and nobody reads those spans. The team wants to stop paying for them. What is the right move?

      1. ACompress the old spans and leave the writer running.
      2. BRaise the alert limit so the feature stops showing up.
      3. CSample one span in ten and keep writing the rest.
      4. DRemove the span writing together with the feature, and delete its old spans.
      Show the answer

      Answer: D

      • A Compression shrinks the cost and leaves a writer for a feature nobody uses.
      • B An alert limit has nothing to do with storage, so the growth goes on.
      • C Sampling keeps writing spans for a retired feature, at a tenth of the cost.
      • D Correct. Logging belongs to the feature, and when the feature is retired the writer and its old spans go too.
